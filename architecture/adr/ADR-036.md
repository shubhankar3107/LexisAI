ADR 36 — Organization-Based Multi-Tenancy

Status: Accepted

Context

LexisAI V1 is a single-tenant document-processing system.

V2 must support multiple organizations while ensuring strict tenant isolation.

Users may belong to multiple organizations, and each organization may contain multiple users.

Documents and future AI resources must belong to an organization rather than directly to an individual user.

Decision

LexisAI V2 will use organization-based multi-tenancy.

The core ownership model will be:

User
  |
  | OrganizationMembership
  |
Organization
  |
  | owns
  |
Document

An Organization represents a tenant.

A User represents an authenticated identity.

An OrganizationMembership associates a User with an Organization and defines the user's role within that organization.

Documents will become organization-scoped resources.

A document must belong to exactly one organization.

Users will access documents through their membership in the organization that owns the document.

A user may belong to multiple organizations.

Tenant Isolation

All tenant-scoped resources must contain an organization_id directly or have an unambiguous relationship to an organization.

Repository queries for tenant-scoped resources must include organization scope.

A resource must never be returned solely because a user knows its resource ID.

For example, a document lookup must conceptually enforce:

document_id = requested_document_id
AND organization_id = authenticated_organization_id

Authorization must occur before returning or modifying tenant-scoped resources.

Roles

V2 will initially define three organization-level roles:

OWNER
ADMIN
MEMBER

OWNER has full organization control.

ADMIN has administrative permissions within the organization but does not own the organization.

MEMBER has normal access to organization resources according to application-level permissions.

Authentication and Authorization

Authentication identifies the user.

Authorization determines whether the authenticated user can perform an operation within a specific organization.

JWT access tokens will identify the authenticated user.

Organization membership will be used to determine the user's access to a tenant.

A client-provided organization_id must never be trusted without validating that the authenticated user belongs to that organization.

Document Ownership

The existing V1 Document model will be extended to become organization-scoped.

The relationship will become:

Organization
    |
    +── Document
          |
          +── DocumentAsset
          +── DocumentContent
          +── DocumentChunk

Document ownership will be represented by organization_id on the Document model.

This allows existing document assets, extracted content, and chunks to inherit the document's tenant boundary.

Future AI resources such as embeddings, vector records, summaries, extracted entities, and audit records must follow the same organization boundary.

Security Invariants

1. Every tenant-scoped resource belongs to exactly one organization.
2. Every protected request has an authenticated user.
3. Access to an organization requires valid membership.
4. Resource access must be scoped to the user's organization.
5. Resource IDs alone are insufficient for authorization.
6. Cross-organization access must be rejected.
7. Tenant isolation must be enforced consistently across repositories, services, and APIs.
8. Future AI and vector data must preserve the same tenant boundary.

Consequences

Positive:

- Supports multiple organizations.
- Supports users belonging to multiple organizations.
- Provides a clear foundation for RBAC.
- Establishes tenant isolation before AI features are introduced.
- Allows future billing and usage tracking to operate at organization level.
- Allows organization-specific AI configuration.
- Provides a clean foundation for enterprise features.

Negative:

- Existing document queries must become organization-aware.
- Existing document APIs will eventually require authentication.
- Additional database relationships are required.
- Authorization logic becomes more complex.
- Cross-tenant isolation requires explicit testing.

Deferred

The following are intentionally deferred:

- Custom roles
- Fine-grained permissions
- Team-level permissions
- SSO/SAML
- SCIM
- Service accounts
- API keys
- Cross-organization sharing
- Organization billing
- Usage quotas
- PostgreSQL Row-Level Security

These can be introduced later without changing the fundamental organization-based tenancy model.

Migration Strategy

V1 remains unchanged and is preserved by the v1.0.0 Git tag.

V2 will introduce organization support through database migrations.

Existing V1 documents will be handled through an explicit migration strategy rather than silently assigning ownership.

No V2 migration will modify the historical V1 release.

Summary

LexisAI V2 adopts organization-based multi-tenancy.

Users belong to organizations through memberships.

Organizations own documents.

Documents and their dependent resources inherit the organization's tenant boundary.

Authentication identifies the user, while authorization validates organization membership and resource ownership.
