ADR-007

Title

A Document can have multiple content representations

⸻

Status

Accepted

⸻

Problem

A document initially contains only one extracted text representation.

However, future versions of LexisAI may generate multiple representations of the same document, such as:

* OCR text
* Cleaned text
* Markdown
* HTML
* AI-structured JSON
* Translations
* Other derived content

If we store only a single text field in the Document entity, future expansion becomes difficult and violates the Single Responsibility Principle.

⸻

Options Considered

Option A

One DocumentContent per Document.

Document
    │
    ▼
DocumentContent

Advantages

* Very simple.
* Easy to understand.

Disadvantages

* Difficult to support multiple content formats.
* Requires schema changes later.
* Couples the document to a single representation.

⸻

Option B (Chosen)

Allow a document to own multiple content records.

Document
      │
      ▼
DocumentContent
      │
      ├── RAW_TEXT
      ├── OCR_TEXT
      ├── CLEAN_TEXT
      ├── MARKDOWN
      ├── HTML
      ├── TRANSLATED_TEXT
      └── STRUCTURED_JSON

⸻

Decision

The relationship will be:

Document (1)
↓
DocumentContent (N)

Each DocumentContent represents one specific representation of the document.

The type of representation will be identified using a content_type enum.

⸻

V1 Business Rule

Although the architecture supports multiple content records, V1 will create only one:

RAW_TEXT

No additional content types will be implemented in V1.

⸻

Why We Chose This

This design:

* Keeps the Document entity focused on business information.
* Allows new content representations without redesigning the schema.
* Supports future AI features such as OCR, translation, markdown generation, and structured extraction.
* Aligns with our principle of designing for extensibility while implementing only current requirements.
